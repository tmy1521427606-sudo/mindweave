# 个性化知识库学习 Agent 设计

## 目标

在现有本地认知日报上形成一个可验证的单机闭环：用户阅读更详细的新闻，使用收藏和兴趣反馈塑造主题偏好，通过跨期搜索回溯历史，并可向豆包对话 Agent 追问。Agent 优先使用本地新闻与知识卡片；资料不足或问题明确要求最新信息时联网检索；联网取得且可追溯的内容经过抽取、去重和可信度判断后沉淀到本地知识库。

当前版本不支持账号、跨设备同步或多人共享。设计保留清晰的数据和 API 边界，未来多人版本再替换身份、存储、队列和部署组件，不提前建设这些能力。

## 成功标准

- 新闻详情页首先展示事实、背景、事件发展、影响和来源，基础概念保持明显，跨领域连接、风险和 5 分钟行动改为靠后的紧凑辅助区域。
- 用户可对新闻执行收藏、继续跟踪、多推此方向、需要基础、想看技术、想看商业、已了解和不感兴趣等操作；同一操作可取消，状态本地持久化。
- 首页可检索当前一期，也可打开独立弹窗按关键词检索全部历史日报，并跳转到原始详情。
- Agent 能针对当前新闻或全知识库回答，回答明确标记是否使用联网，并为每个事实性结论提供可打开的来源。
- 本地资料相关度不足、资料过期、对象覆盖不完整，或问题包含“最新/今天/刚发布”等时，才触发联网检索。
- 不把模型回答直接当成事实入库。保存来源记录与结构化知识卡片，区分事实、来源方观点、Agent 推断和用户笔记。
- 新闻、反馈和知识数据可导出或由本地文件/SQLite 恢复，满足可回溯要求。

## 产品信息架构

### 日报首页

- 保留今天、昨天和往期入口、日期筛选和本期列表。
- 当前搜索框继续只筛选当前期，并在旁边增加“搜索往期”按钮。
- “搜索往期”打开对话框，输入关键词后展示跨日期结果；结果显示日期、标题、主题、来源和命中摘要。
- 新闻卡片增加收藏与兴趣快捷操作；详细的兴趣选项放在展开菜单中，避免卡片过密。
- 排序在原有推送分基础上增加个性化加分，但界面同时展示“编辑评分”和“兴趣加分”，避免把偏好伪装成客观重要性。

### 新闻详情

展示顺序如下：

1. 标题、日期、来源、主题和评分。
2. 新闻事实。
3. 背景：事件发生前的必要上下文。
4. 事件发展：按时间或因果顺序说明发生了什么变化。
5. 影响：分别说明对行业、从业者或用户的可能影响。
6. 来源方观点和模型对比/连续跟踪（存在时）。
7. 基础概念。
8. 紧凑辅助信息：跨领域连接、风险与不确定性、5 分钟行动。
9. 来源、兴趣反馈和上一篇/下一篇。

历史数据缺少 `background`、`development` 或 `impact` 时不生成空标题；继续用现有字段展示。新日报必须填写这些字段，数据校验测试保证其完整性。

### 学习 Agent

- 页面右下角提供可展开的 Agent 入口，详情页默认携带当前新闻上下文，首页默认面向全部知识库。
- 每个回答显示“仅本地”或“本地 + 联网”，并列出引用来源。
- 用户可展开“本次检索依据”，查看本地命中和联网命中，避免黑箱回答。
- 回答后显示本次新增的知识卡片；低可信来源进入“待核实”，官方文档、论文、政府和项目官方发布在满足规则时可自动进入“已验证”。
- 第一版不做语音、多 Agent 编排、自动微调或开放式网页代理。

### 我的知识库

- “知识卡片”视图按主题、类型、状态和日期筛选。
- “主题 Wiki”是知识卡片的阅读投影，不是独立存储。页面展示定义、时间线、关键参与者、相关事件、未决问题和引用。
- “兴趣画像”展示各主题的反馈证据和分数，用户可以降低、清零或停止跟踪某一主题。

## 兴趣信号

支持以下信号：

| 信号 | 含义 | 默认主题权重变化 |
|---|---|---:|
| `bookmark` | 保存稍后阅读，不等同于持续推送 | +1 |
| `follow` | 后续版本、研究和事件继续出现时提醒 | +3 |
| `moreLikeThis` | 增加相同主题与相邻主题内容 | +2 |
| `needFoundation` | 增加基础解释，不简单提高主题频次 | 深度偏好 -1 |
| `wantTechnical` | 增加实现、论文和工程内容 | 技术角度 +2 |
| `wantBusiness` | 增加商业、运营和市场影响 | 商业角度 +2 |
| `known` | 减少重复基础解释 | 深度偏好 +1 |
| `irrelevant` | 降低该主题，但不屏蔽重大新闻 | -3 |

每条信号必须记录文章、主题、时间和当前是否有效。个性化得分只影响排序和候选配额，重大事件仍可凭编辑评分进入日报。系统不能根据一次点击永久决定画像。

## 检索与回答策略

### 本地检索

对查询同时执行：

- SQLite FTS5 全文检索：适合公司名、模型名、版本号和精确关键词。
- 向量相似检索：适合概念改写和跨领域问题。
- 元数据过滤：限定日期、主题、来源类型、知识状态和当前文章。

合并候选后按以下因素重排：关键词匹配、语义相似度、来源可信度、时效性、当前新闻关联和用户兴趣。第一版数据规模约每天 30 条，可将 embedding 作为浮点数组保存在 SQLite 中并在 Node 进程内计算余弦相似度，不引入单独向量数据库。

### 联网触发

满足任一条件即触发联网：

- 本地最高相关度或综合覆盖低于配置阈值。
- 问题明确包含“最新”“今天”“刚发布”“当前版本”等时效词。
- 本地资料最后更新时间超过问题允许的时效范围。
- 问题包含多个对象，而本地资料没有覆盖全部对象。
- 本地来源相互冲突，需要寻找一手材料核验。
- 用户显式点击“联网核实”。

联网结果优先采用官方公告、官方技术文档、论文、GitHub Release/Commit 和政府机构材料。搜索结果页面或二手报道不能作为唯一证据。

### 回答约束

- 豆包使用火山方舟兼容接口，模型 ID 通过本地环境变量配置，不硬编码具体版本名称。
- API Key 只由本地 Node 服务读取，不进入 HTML、浏览器存储、日志或错误响应。
- 回答必须携带引用 ID；前端将引用 ID 映射到来源标题、日期和 URL。
- 无法找到可靠资料时直接说明资料不足，不编造结论。
- 事实、来源观点和 Agent 推断分别标注。

## 知识沉淀

### 三层模型

1. **来源层**：保存 URL、标题、发布者、发布日期、获取时间、来源类型、短摘录、内容指纹和访问状态。对受版权保护的页面不复制全文。
2. **知识卡片层**：保存原子化事实、概念、事件、对比或关系，携带来源引用、有效时间、置信状态和生成模型。
3. **个人认知层**：保存收藏、兴趣信号、用户提问、用户笔记、已掌握概念和学习深度偏好。

知识状态为：

- `verified`：可靠一手来源支持且没有已知冲突。
- `needs_review`：来源质量一般、存在冲突或内容由 Agent 推断。
- `rejected`：用户否决或证据失效，不参与默认回答。
- `superseded`：被更新版本取代，仍保留以便回溯。

写入流程为：抓取来源元数据 → 内容指纹去重 → 提取知识卡片 → 与现有卡片进行实体/语义去重 → 判断状态 → 写入 → 更新相关 Wiki 投影。知识卡片不可覆盖旧卡片，只能建立替代或冲突关系。

## 数据与持久化

第一版本地实现采用 Node.js 24 的内置 `node:sqlite`，避免额外数据库服务。

现有 `data/*.json` 继续作为日报的可读、可版本化归档。SQLite 是检索、反馈、对话和知识沉淀索引；启动或更新后根据文章 ID 与内容指纹增量同步 JSON，不重复写入。

核心表：

- `articles`：日报文章、详细字段和来源元数据。
- `article_topics`：文章与主题多对多关系。
- `interest_signals`：文章级与主题级反馈。
- `sources`：联网或日报的一手来源记录。
- `knowledge_cards`：可检索的原子知识。
- `knowledge_card_sources`：知识卡片与来源证据。
- `embeddings`：文章或知识卡片向量。
- `conversations`、`messages`：本地对话历史。
- `card_relations`：支持、冲突、替代和相关关系。

数据库默认保存在项目的 `var/cognitive-daily.sqlite`，并由 `.gitignore` 排除。提供 JSON 导出，方便迁移和恢复。

## 本地服务 API

- `GET /api/health`：返回数据库与豆包配置状态，不暴露密钥。
- `GET /api/search?q=&scope=all`：跨期全文搜索。
- `GET /api/profile`：返回主题兴趣与深度偏好。
- `PUT /api/articles/:id/signals/:signal`：启用一个兴趣信号。
- `DELETE /api/articles/:id/signals/:signal`：取消一个兴趣信号。
- `POST /api/chat`：提交问题和可选的当前文章 ID，返回回答、引用、是否联网和知识卡片。
- `GET /api/knowledge`：筛选知识卡片。
- `GET /api/wiki/:topic`：返回主题 Wiki 投影。
- `POST /api/knowledge/export`：导出来源、卡片、兴趣和对话元数据。

第一版采用普通 JSON 响应，不做流式输出；先验证答案质量和引用，再决定是否增加 SSE。

## 每日更新

每日更新脚本可以由 Windows 任务计划程序运行，浏览器无需打开。流程为：

1. 读取兴趣画像和持续跟踪主题。
2. 在限定开放来源中收集候选。
3. 去重、核验日期和一手来源。
4. 根据编辑评分、兴趣分和内容配额选出不超过 30 条。
5. 生成日报 JSON，保留来源与事实/观点/推断边界。
6. 同步 SQLite、生成 embedding 并更新 Wiki。

定时任务、抓取范围和联网费用在 UI/Agent 闭环验证之后实施；第一阶段不要求后台更新即可完成验收。

## 错误与安全边界

- 豆包未配置或请求失败时，历史搜索、收藏、兴趣画像和本地知识检索仍可使用。
- 联网搜索失败时，不用旧资料冒充最新答案；明确告诉用户未完成联网核验。
- 所有写接口限制请求体大小、验证枚举和 ID，不允许任意文件路径。
- 外部页面内容视为不可信数据，不能作为系统指令执行。
- URL 只允许 `http`/`https`，显示时进行 HTML 转义；不保存网页脚本。
- 日志记录请求 ID、耗时、使用模型和错误类别，不记录 API Key 或完整私人问题。

## 测试

- 单元测试覆盖兴趣互斥/叠加、画像计算、FTS 检索、向量相似度、联网触发条件、来源去重、知识状态和引用完整性。
- API 集成测试使用临时 SQLite 和伪造豆包/搜索客户端，不产生真实费用。
- 前端 DOM 测试覆盖跨期搜索弹窗、收藏状态、详情层级、Agent 本地/联网标签和错误退化。
- 数据校验要求新日报文章具有背景、发展、影响和可访问的一手来源。
- 手工验收至少包括：历史关键词搜索、刷新后反馈保留、针对当前文章追问、最新问题触发联网、知识卡片可回溯到来源。

## 未来多人版本迁移边界

未来部署给多人使用时，保持 API 语义和核心实体不变，替换以下组件：

- SQLite → PostgreSQL + pgvector（按用户/租户隔离）。
- 本地单进程 → Web API + 后台任务队列。
- 本地固定用户 → 登录、授权、配额和审计。
- Windows 计划任务 → 服务端调度器。
- 本地文件归档 → 对象存储与备份。
- 单机密钥 → 服务端密钥管理和按用户用量计费。

第一版不为这些未来组件添加空抽象；仅通过稳定的数据字段和 HTTP API 避免 UI 与存储直接耦合。
